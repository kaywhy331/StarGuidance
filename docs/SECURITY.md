# Security and privacy

Birth facts, derived profiles, private questions, follow-ups, and free-text feedback are sensitive.

## Implemented controls

- AES-256-GCM envelopes use a random 96-bit nonce and authentication tag; tampering fails authentication. Envelopes are additionally bound to an associated-data context (`<data-class>:<owner user id>`), so a database-level splice of one user's ciphertext into another user's row — or a question into a profile column — fails the tag check instead of decrypting. Pre-binding envelopes remain readable until the next key rotation rewrites them; the residual boundary is that same-class, same-owner envelopes remain interchangeable, since several classes are encrypted before their row exists.
- Runtime selection fails closed. The local adapter requires `RUNTIME_ADAPTER=local`, `ALLOW_LOCAL_RUNTIME_ADAPTER=true`, a development/test `APP_ENV`, and no hosted Netlify context.
- Supabase Auth is verified server-side with `auth.getUser()`. Routine access uses email/password credentials; passwords are never persisted or logged by the application. Optional signup-confirmation and password-recovery links terminate at a same-site callback, and account deletion also removes the Supabase Auth identity through a server-only service-role client.
- Signup requires versioned Terms, Privacy Notice, and 18+ acknowledgements. Receipts are first bound to Auth `app_metadata`, then mirrored into the subject-scoped consent table when the application user is provisioned. A version mismatch routes the user through re-consent before new profile/reading/commerce creation. Optional marketing consent is independent and reversible; migration `0015` preserves every grant/withdrawal cycle while a partial unique index permits only one active grant. Profile personalization has its own versioned consent.
- The account-free trial is isolated from authenticated persistence. A browser-generated random UUID is bound to a one-year HMAC-signed HttpOnly marker; this is not a hardware fingerprint. A redundant local marker improves the ordinary cleared-tab path. The guest endpoint requests no birth data, uses the deterministic provider only, and returns neither the raw question nor arbitrary generated markup. It keeps the exact question and locked draw only inside a seven-day AES-256-GCM receipt stored by the browser, with display data limited to session storage. Signup/sign-in can present that opaque bearer receipt to recover the exact draw for a same-card follow-up; it is never silently imported into account history.
- Guest automation protection uses the edge-authenticated address only when the hosting boundary supplies one. The address is immediately HMACed with the guest secret, then the existing distributed limiter hashes that opaque key again before Postgres storage; the raw address is not retained in the application's quota table. An unresolved edge address opts out rather than combining every visitor into one bucket. The signed browser marker remains the one-reading boundary so shared households are not permanently denied by IP. Deleting both cookie and browser storage can reset that soft boundary; the project deliberately does not add covert fingerprinting to prevent that privacy-preserving limitation.
- Password recovery succeeds only after the verified callback issues an encrypted, user-bound, 15-minute receipt. Updating the password consumes that receipt and attempts global session revocation; ordinary sign-out uses explicit local scope and surfaces provider failure.
- The Supabase repository encrypts raw profiles, calculation payloads, questions, follow-ups, feedback comments, and temporary report-generation sources with AES-256-GCM before SQL persistence. The managed key remains outside Postgres. A pending Stripe order carries only the minimized derived traits, tensions, and calculation output needed for its report—never birth name/date/time/place or numerology name rendering. Fulfillment moves that source into the report job atomically; success or a terminal payment event clears it, and key rotation covers both temporary locations.
- Derived profile snapshots contain only calculation output and trait provenance. Migration 0005 scrubs the legacy plaintext name/date/place metadata copy before adding profile, follow-up, and reading-idempotency constraints.
- Browser JWTs have no private-table privileges. User-scoped SQL transactions assume the non-login, non-inheriting `starguidance_app` role and set only the subject obtained from verified Supabase Auth. RLS is forced on user-owned tables; anonymous/public access is revoked. Both background queues are subject-bound for the application role (migrations `0008` and `0012`): request-path transactions can reach only their subject's job rows, while cross-user claim/complete/fail sweeps run as the owning connection role under explicit named policies—the same trust boundary as the payment-webhook lease.
- Mutating browser routes validate Origin/Host. Rate limits on the `supabase` runtime adapter are enforced by a distributed, Postgres-backed function (migration `0006_rate_limit_buckets`, forced RLS, `starguidance_app`-only); the `local` adapter (dev/test) keeps an in-process limiter. Netlify uses its overwritten client-IP header; another edge must explicitly configure one approved overwritten header, while spoofable `x-forwarded-for` is always ignored. Stripe webhooks are exempt from Origin checks and require signature verification.
- Every API response receives `Cache-Control: private, no-store, max-age=0`; sensitive read failures distinguish an expired session from an internal retrieval failure so a database fault does not spuriously redirect the user through login.
- Profile-engine bearer authentication is enabled whenever `PROFILE_ENGINE_SHARED_SECRET` is configured. In staging and production, startup rejects a missing or trivially weak secret before serving traffic.
- The profile-engine container disables Uvicorn access logs, and its application does not log request bodies, response bodies, birth inputs, authorization headers, or derived calculations. `/health` remains public and contains no private data.
- Public web `/api/health` is dependency-free liveness. Deep readiness requires a domain-separated HMAC bearer keyed by its own `READINESS_PROBE_SECRET` before it probes configuration, Postgres/RLS, or the profile engine. It does not accept the profile-engine or worker secret. Tests assert that environment values, dependency errors, request bodies, and response bodies are absent from both responses.
- `POST /api/internal/interpretation-jobs` requires its own domain-separated HMAC bearer token (a distinct context string from the readiness probe's) before it drains interpretation or paid-report jobs; a missing or weak `INTERPRETATION_WORKER_SECRET` fails the route closed with `401` rather than accepting an unauthenticated trigger.
- First-party `product_events` contain no subject ID or content. Application schemas and database checks enforce closed event/property vocabularies; request idempotency values are SHA-256 digested before storage, browser roles have no privileges, and only aggregate counts leave the operations boundary. Operational alert payloads contain fixed classes, severities, counts, thresholds, and environment only. The optional receiver must be HTTPS, and its URL is never logged or returned.
- Safety classification occurs before a draw for crisis, compulsive-redraw, and guarded high-stakes language. A guarded question first returns a no-reading/no-draw/no-job preflight and proceeds only after explicit reflective-scope confirmation. A configurable normalized same-question cooldown checks only the authenticated user's encrypted reading history server-side and returns the retained reading without creating another draw.
- The draw function accepts no profile snapshot, trait, question, prompt, or AI input.
- AI input is designed to contain only a locked draw, curated meanings, the private question, and a compact stable trait lens. Birth name/date/time/place, email, and raw calculations are excluded.
- Direct Groq and custom-gateway credentials are separate fail-closed modes. A custom endpoint requires an explicit TokenPak transport, exact pinned HTTPS hostname ending in `/v1`, an approval flag, distinct gateway bearer, and the complete Cloudflare Access service-token pair. The app refuses loopback/IP/userinfo/query/fragment/custom-path origins, refuses Access credentials on direct Groq, and refuses a retained Groq key in gateway mode. Access headers are sent only to the approved custom origin. The default-off blueprint validates only StarGuidance reading/follow-up prompts and schemas, canonicalizes provider envelopes, bounds bodies/time/concurrency/rate/input-plus-output tokens, disables TokenPak retries/recovery/persistence/enrichment, and injects the Groq key only in a fixed egress broker. Raw TokenPak is never an approved tunnel origin; the remaining host, Cloudflare, log-purge, pilot, and rollback contract is in [AI gateway and tunnel security](AI-GATEWAY-SECURITY.md) and [the Cali pilot runbook](CALI-TOKENPAK-PILOT.md).
- Live generation requires an explicit model-safety approval flag. A deterministic post-generation validator rejects prohibited factual or guaranteed death, pregnancy, diagnosis, verdict, guilt, infidelity, private-third-party, investment-return, employment, and invented profile-system value claims even when a provider response is schema-valid; rejection uses the deterministic fallback and never redraws.
- History previews are decrypted only for an authenticated response; no question preview is stored in plaintext.
- Authenticated export reads only through user-scoped repositories, then decrypts for that response; it includes feedback and purchased report content even when access has since been revoked. Profile deletion removes birth snapshots and readings but deliberately preserves paid commerce/report records with nullable snapshot pointers, including recoverable fulfillment already paid or in Checkout. Account deletion verifies the current password, deletes the hosted Auth identity first, and relies on the enforced database cascade to remove all subject-owned application rows so a usable identity is never stranded after a partial two-step deletion.
- Deletion leaves a cascade-proof tombstone (migration `0010`): after re-authentication and before the Auth identity is deleted, a user-less `deletion_receipts` row records a domain-separated hash of the subject, the policy version, and the request time. Deletion aborts if the receipt cannot be written. The application role may only append receipts; reads belong to the owning connection role. Sign-in, sign-out, and password changes write best-effort `audit_events` rows that never block the auth action itself.
- Reading session and draw writes are one database transaction. Active deck/spread flags are consulted before creation. Outputs are separate append-only rows, so failure, retry, refresh recovery, and follow-up cannot replace the locked assignments. Concurrent follow-up inserts serialize on the owned reading row before applying the configured count limit.
- Structured topic/intent/horizon classification, the versioned entitlement decision, expiry, and monotonic cut/reveal progress are persisted with the reading (migration `0016`). Server state is authoritative for interrupted recovery; browser session storage is only a fallback and cannot move reveal progress backward or alter the draw.
- Optional in-scene narration is client-only and selects only a browser voice explicitly marked `localService`; if no device-local English voice exists, the spoken-paced word reveal continues silently. Reading text is never submitted to a network-backed speech service by the application.
- Stripe events are signature checked, claimed with a failure-releasable durable lease, and resolve user/snapshot ownership from the persisted order rather than trusting webhook metadata. Paid fulfillment atomically marks the order paid, grants one entitlement, creates one pending report, enqueues one durable job, and clears the order source; replay returns the existing report. Full refunds and disputes revoke the entitlement, clear any temporary source, and require report reads to remain withheld.
- Oracle streaming emits only schema-validated persisted result phases; the private question is not included in the stream URL or payload.
- The deploy-preview composition contains synthetic cards and text only, is `noindex`, and is enabled by a Netlify deploy-preview-only flag that defaults off on public production.
- New report purchases and Stripe webhooks fail closed behind a server-side environment gate that defaults off, the published feature policy, and the active product record. The server returns only the effective capability to the UI; no public flag can authorize commerce.
- Purchased-report history and `/api/reports/[id]/pdf` require the same authenticated entitlement checks as the web report. The PDF is generated from the shared presentation model and does not create a public storage object or unauthenticated artifact URL.
- Operational access is not inferred from a browser claim. Server-only `SUPPORT_USER_IDS` and `OPERATOR_USER_IDS` UUID allowlists gate aggregate diagnostics and masked exact-ID status. Trace results exclude subject IDs and content. Operator-only retry is same-origin, rate-limited, row-state constrained, and audited. Runtime configuration rows are forced-RLS/app-only; a different operator must approve each draft before publication, rollback is version-preserving, and emergency controls can only disable AI/models/payments. Direct content activation changes are closed-target, audited, and affect new sessions only.

## Production gates

Netlify Deploy Preview #4 is the credentialed non-production staging lane. A protected run must pass migration/seed rehearsal, forced-RLS and two-user isolation, Auth-backed provisioning, encrypted profile and reading persistence, locked-draw recovery, export, account/Auth deletion, profile-engine authorization, cleanup, redaction, and accessibility checks at the exact commit being promoted. Evidence from an earlier commit does not transfer, and staging evidence does not approve production.

The remaining security and operations gates are:

- owner-managed key generation/escrow plus a credentialed rehearsal of the implemented dual-read/batched re-encryption procedure;
- owner-approved private-data durations and scheduling for the guarded retention command;
- an owner-inbox rehearsal of optional signup confirmation and password recovery, including a cross-browser token-hash callback;
- hosted Netlify, Supabase, Render, and AI-provider log-retention review by an operator with dashboard access;
- Stripe test credentials and a public webhook/Checkout/refund rehearsal against durable order and entitlement storage;
- provider no-retention contracts, production redaction sampling, backup/restore, incident response, and regional crisis resources;
- ownership and rehearsal of the implemented aggregate alert receiver plus provider-native uptime/database/billing alerts and independent review — `main` branch protection and required checks are enforced (verified 2026-08-06), and distributed rate limiting for serverless instances is implemented on the `supabase` runtime adapter (Postgres-backed, migration `0006_rate_limit_buckets`, verified 2026-08-06);
- legal-owner review of the versioned beta Terms, Privacy Notice, age policy, retention schedule, and launch regions.
- configuration of a distinct managed `GUEST_TRIAL_SECRET`, followed by desktop/mobile/private-browsing tests of marker expiry, storage-cleared behavior, account handoff, shared-network limits, and seven-day receipt expiry at the exact candidate commit;

The concrete role boundary, key-rotation commands, CI logical restore, guarded retention tool, telemetry boundary, and incident procedure are documented in [Operations and recovery](OPERATIONS.md).

Never put birth data or questions in URLs, analytics, breadcrumbs, logs, support screenshots, or unauthenticated storage. The committed `.env.example` contains names only and no credentials.
