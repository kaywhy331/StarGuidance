# Known gaps and production gates

This branch is a safe-beta candidate, not a public-production approval. The implemented security boundaries are useful now: conventional email/password Auth, versioned consent receipts, encrypted profile/question storage, forced-RLS user isolation, database-enforced snapshot immutability (guard trigger plus narrowed grants, migration 0009) with application-enforced draw lineage, deterministic AI fallback, output safety validation, scoped export/deletion, security headers, and fail-closed runtime selection. The gates below are deliberately explicit so a green build cannot be mistaken for business, legal, operational, or provider approval.

## Exact-commit release evidence

- Migrations `0005_bumpy_moon_knight` through `0016_reading_intake_recovery` must be applied to the non-production Supabase staging project. `0005` scrubs legacy plaintext birth metadata and adds profile-root, initial follow-up, and reading-idempotency constraints; `0006`–`0010` add distributed rate limiting, durable interpretation jobs, subject-bound job policy, snapshot immutability, and deletion receipts; `0011` adds deck/spread kill switches and configurable follow-ups; `0012` adds the forced-RLS report queue and profile-independent commerce retention; `0013` stages the encrypted derived report source before Checkout; `0014` adds account settings and versioned consent withdrawal; `0015` preserves grant/withdraw/re-grant history while allowing only one active grant; `0016` persists structured intake classification, entitlement decisions, monotonic ritual progress, and expiry. The protected workflow must then prove schema readiness, two-user isolation, both queues, locked-draw/server-recovery behavior, export, deletion/payment separation, key rotation/rollback, synthetic cleanup, and the deployed commit.
- Public `/api/health` proves only liveness. The protected HMAC-authorized readiness probe must pass for the exact deploy being promoted; an earlier green run does not transfer to a later commit.
- Full Node 24 CI, desktop/mobile Chromium plus desktop Firefox/WebKit E2E, Python 3.12 checks, hashed lock installs, production dependency audit, migration rehearsal, secret scan, and Netlify deployment must all be green at the same head.
- `main` now enforces required status checks (`web`, `profile-engine`, `e2e`, `secret-scan`, `migration`, `guard`, `verify`), PR-only merges, required conversation resolution, and blocked force-push/deletion, including for administrators (applied and verified via the GitHub API 2026-08-06). CI supplies neutral PR liveness paths for the legacy `guard`/`verify` contexts so ordinary PRs do not wait forever on the dispatch-only protected workflow; credentialed staging evidence remains a separate promotion gate. Required approving reviews remain set to zero: GitHub never counts a PR author's own approval toward that count, and no second reviewer is configured yet. The draft PR must not be merged by this implementation lane until an independent reviewer is assigned.

## Product-flow gaps

- Live interpretation now runs through a durable, idempotent job (migration `0007`, `packages/database/src/interpretation-jobs.ts`): the draw-creation request enqueues the job in the same transaction as the reading and draw, then makes one best-effort inline attempt to keep today's near-synchronous latency in the common case. One claimed job attempt may try the reviewed Groq model chain, but all model calls share one 40-second deadline and the same immutable draw; no model retry can reshuffle cards or create another job. If the bounded chain falls back deterministically, that completed reading is persisted rather than retried. Durable job retry remains available only when the job attempt itself is interrupted or fails before a result is persisted, applying capped backoff while preserving the locked draw. Result writes lock the reading and preserve the first authoritative output if an expired attempt overlaps a reclaim. If the inline attempt is interrupted, the job stays durably claimable — a Netlify-scheduled function (`netlify/functions/process-interpretation-jobs.mts`, every minute) calls the bearer-secret-protected `POST /api/internal/interpretation-jobs`, which claims and processes one interpretation immediately before its work begins so a bounded model chain cannot leave later jobs holding expired leases or overrun a serial batch request. The scheduler continues draining remaining work on subsequent minute ticks; the client (`apps/web/src/app/session/[id]/reading-scene.tsx`) polls while work is pending. Requires `INTERPRETATION_WORKER_SECRET` configured wherever the "supabase" runtime adapter runs, and `NEXT_PUBLIC_APP_URL` resolvable from the Netlify Functions runtime (not just the browser) so the scheduled function knows where to call back. Standalone Netlify Functions cannot import `postgres`/`drizzle-orm` at all — Netlify's zip-it-and-ship-it bundler fails to resolve them at runtime (`netlify/zip-it-and-ship-it#869`, confirmed here across three bundler configurations) — which is why the actual claim/AI-call/write work runs behind the Next.js/Postgres path instead of in the scheduled function itself.
- The sanctuary offers an explicit deck-cut choice (Cut / Skip cut), intentional per-card click/tap/keyboard reveal with a Reveal-all convenience control, an early Finish-shuffling control, and account-backed motion/sound controls that fall back to the OS/local preference. A separate display name appears in the reading experience and is never derived from the encrypted birth name. Cut choice and revealed indexes recover from server-backed monotonic progress even after browser session storage is cleared; the versioned session TTL reaches an explicit expired/recovery state. Completed history entries open a direct pre-revealed result route. Automated coverage does not replace the manual keyboard/screen-reader/real-device review below.
- Intake records an explicit topic, intent, and horizon, and supports an approved question-free general reading. Guarded medical/legal/financial and similar questions return a no-draw preflight and lock cards only after “Continue as reflection.” Follow-up count and normalized same-question cooldown remain server-configurable. Reading access can be `unlimited` or a durable free-window allowance (`READING_FREE_ALLOWANCE` / `READING_ALLOWANCE_WINDOW_HOURS`), and every reading stores the versioned decision. A paid reading tier and cross-account abuse signal remain product/policy decisions rather than hidden assumptions.
- Private resonance/helpfulness/comment feedback is implemented, encrypted, and included in export. Scheduled outcome reminders and the separate occurred/partial/did-not-occur/unclear research schema are intentionally not represented by this MVP feedback: RES-008 is deferred pending reminder consent, retention, notification, and research-governance decisions; RES-009 becomes applicable when that outcome surface is activated.
- Reading history shows spread display names plus follow-up, feedback, and profile-report state. Reports expose pending/ready/failed pages, authenticated same-purchase retry, and standalone purchased-report history. The role-separated operations console provides aggregate queue status, fixed failure classes, exact opaque trace lookup, and read-only effective model/report/allowance configuration without questions, profiles, user IDs, report content, or raw errors. Operators can rate-limitedly retry retained failed jobs and every retry is audited. Runtime config mutation and rollback deliberately remain reviewed deployment operations; no browser console is authorized to change them.

## Reports and commerce

- New reports are hidden and checkout/webhooks fail closed unless `ENABLE_PROFILE_REPORTS=true`; button visibility separately requires `NEXT_PUBLIC_ENABLE_PROFILE_REPORTS=true`. Both default false and should remain false in the safe beta.
- Stripe signature, reconciliation, replay, refund, dispute, entitlement, and revocation behavior has automated coverage, but credentialed test Checkout/webhook/refund UAT is still required in an isolated commerce deployment.
- Stripe fulfillment atomically grants one entitlement, creates one pending report, and enqueues one durable report job before acknowledging the verified event. The scheduled drain retries with capped backoff; the UI polls explicit pending/ready/failed states and can re-enqueue the same retained source without another charge. The credential-free local adapter remains intentionally synchronous. Public launch still requires credentialed Stripe lifecycle UAT, optional notification policy, and finance approval.
- The authenticated PDF is generated from the same presentation model as the web report and carries document language, metadata, and tagged H1/H2/paragraph structure; automated tests assert structure and source parity. It still requires independent screen-reader/PDF-UA review before being described as fully accessible. Pricing, taxes, receipts, refunds/chargebacks, finance retention, support ownership, and launch-region policy remain owner decisions.
- Supabase Storage is not used. If report/PDF artifacts are later stored there, private buckets and object-level RLS need their own reviewed migration and isolation tests.

## Authentication, privacy, and operations

- Routine login uses email and password and sends no email. The owner must choose whether signup confirmation is required; if it is disabled, addresses are not verified. If enabled, the registration notice can request a fresh confirmation without another signup attempt, but delivered confirmation and recovery links still need an owner-inbox, cross-browser smoke test using the reviewed token-hash templates.
- Required service-policy versions are checked before new profile, reading, follow-up, or report-purchase creation. Re-consent is explicit; optional marketing consent is independent, reversible, and preserved as grant/withdrawal history. Account settings persist a display identity and reading preferences. The copy and policy versions remain owner/legal approval gates.
- Support/operator access is a server-only UUID allowlist, not a client role claim. Support sees only aggregate operations and opaque trace status; operators add audited failed-job retry. Named staff assignment, access-review cadence, incident escalation, and production identity lifecycle remain owner operations gates.
- Request limits are bounded and ignore spoofable `x-forwarded-for`. On the `supabase` runtime adapter they are now enforced by an atomic Postgres function (migration `0006_rate_limit_buckets`, one round trip, `starguidance_app`-only, forced RLS) instead of an in-process map, so limits hold across multiple serverless instances; a failed check fails closed as `503`, while `429` is reserved for a quota the caller actually exhausted. Netlify uses its overwritten connection-IP header; another host can opt into one approved provider-overwritten single-value header, otherwise anonymous traffic intentionally shares `client:unresolved`. The `local` adapter (dev/test) keeps the original in-process limiter. Covered by `packages/database/src/rate-limits.integration.test.ts` including a concurrency test, plus `apps/web/src/lib/request-security.test.ts` for the local path.
- The current Netlify account tier does not allow deploy-context variables to combine hidden-secret metadata with server-only scopes. Staging values remain managed, uncommitted, and restricted to the Deploy Preview context, but Netlify requires them to be available to every provider scope. Production requires a plan/configuration that marks sensitive values secret and restricts them to the build/function/runtime scopes that actually need them, followed by a redeploy and protected readiness verification.
- Provider dashboard review remains outstanding for Netlify, Supabase, Render, the AI provider, Stripe, and any telemetry vendor: retention, region, training use, subprocessors, role access, deletion/export, logs, backups/PITR, and incident auditability.
- Production still needs managed key generation/escrow and cutover, provider-hosted restore rehearsal with approved RPO/RTO, approved retention schedules, named responders, customer-support procedures, privacy-safe traces/metrics/alerts, and regional crisis resources.
- The versioned beta Terms, Privacy Notice, 18+ policy, profile-personalization disclosure, deletion behavior, and consent language are engineering controls and draft copy—not legal advice or counsel approval. A responsible legal/privacy owner must approve them for selected launch regions.

## AI, calculations, and content

- Deterministic interpretation is the safe default. Live Groq remains disabled unless `AI_SAFETY_EVALUATION_APPROVED=true`. The reviewed chain is GPT-OSS 120B strict schema, Llama 3.3 70B JSON mode with full application validation, GPT-OSS 20B strict schema, then deterministic fallback; authentication failures skip the remaining Groq models, and every other attempt remains inside one bounded deadline with the original locked draw. Schema-valid output that asserts unsupported numerology, natal, BaZi, Dreamspell, or Nine Star Ki values falls back or advances to the next reviewed model. Production still needs a signed safety/grounding evaluation for every enabled model, broader restricted-profile-leakage evaluation, no-retention contract/configuration, redaction verification, and approved cost/latency budgets.
- Western astrology, BaZi, and planetary angularity correctly return unavailable. Explicit `available | unavailable` service contracts now cover positions/aspects/angles/Whole Sign and Placidus states, four pillars and boundary conventions, and versioned WGS84 angular lines; this is contract readiness, not calculation validation. Licensing, geocoder/historical-timezone handling, approved reference suites, and named expert review remain activation gates.
- Pythagorean v3, Dreamspell v2, and Nine Star Ki now have digest-pinned 60/60/100-case internal regression matrices, including component-wise master numbers, Latin-Extended names, leap dates, non-leap centuries, and every fixed monthly Nine Star Ki boundary. These internal worksheets are not approved independent sources: Dreamspell remains `implemented_pending_approved_reference_dataset`, Nine Star Ki remains convention-bound pending independent reference review, and numerology still needs domain-owner certification. All spiritual-system copy and artwork need a final commercial rights/attribution register and domain-owner approval.
- Automated accessibility tests and cross-browser E2E do not replace manual keyboard/screen-reader/text-zoom review, independent tagged-PDF review, or real-device animation/performance testing. Deploy-preview toolbar frames are excluded only because they are host-injected; the suite separately asserts that the application embeds no frames.
