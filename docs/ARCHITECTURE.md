# Architecture

StarGuidance is a modular pnpm monorepo. Next.js owns product orchestration, FastAPI owns deterministic profile calculations, and independent packages own draw, state-machine, persistence, UI, and narration boundaries.

## Account-free trial flow

The public `/free-reading` lane intentionally does not create an anonymous user, profile, database reading, or AI-provider request. After current Terms, Privacy Notice, age acknowledgement, explicit question confirmation, and spread confirmation, `POST /api/guest-readings` returns an encrypted ceremony containing a server seed and exposes only its commitment. It contains no final cards. The browser creates its CSPRNG nonce before the visual shuffle, mixes in a fresh independent contribution for every stir, and preserves the pending value through session recovery. The reader completes or skips the shuffle and optional cut, then that nonce finalizes the assignment. Only then does the server return an opaque seven-day AES-256-GCM receipt containing the exact locked draw, deterministic result, classification, and confirmed question. Display recovery uses session storage; the encrypted receipt uses local storage for exact-draw recovery and explicit account handoff.

A browser-generated random UUID and signed HttpOnly cookie enforce the normal one-reading allowance without fingerprinting. A trusted-edge network address, when available, is converted to a keyed digest and passed through the shared distributed rate limiter only as an automation backstop; it does not choose cards or become a user identity. After signup, sign-in, email confirmation, or policy re-consent, the allow-listed `/free-reading?continue=1` return path sends the opaque receipt to an authenticated continuation endpoint. That endpoint decrypts the receipt server-side, reconstructs the same versioned cards, and answers the follow-up deterministically, optionally with the authenticated user's minimal private trait lens. It does not redraw, call live AI, or silently add the guest artifact to account history.

## Request flow

1. An authenticated user submits birth facts to the web server; no sensitive field enters a URL.
2. The web server calls the profile engine over a server-to-server boundary. A shared bearer secret can be required.
3. The engine returns versioned numerology, Dreamspell, Nine Star Ki, typed discriminated capability results for Western astrology, BaZi, and planetary angularity, stable/uncertain traits, explicit tensions, and explicit cross-system convergence records. Inactive in-scope systems remain explicit unavailable components rather than fabricating output; their activation contracts require engine/data/convention evidence, uncertainty, and resolved context before an `available` result can cross the boundary. Proprietary systems that forbid the intended use are omitted.
4. The web server encrypts raw inputs and calculation payloads and creates an immutable snapshot.
5. Reading intake reviews the user's exact question and may offer—but never silently apply—a user-centered reformulation. The user confirms the final wording and a spread before any draw. The server snapshots every selected position, its function, reversal preference, personalization mode, and spread capabilities. Safety classification happens before the ritual; crisis language interrupts, while guarded high-stakes questions require explicit reflective-scope confirmation.
6. The server evaluates reading access and active versioned content, creates a 32-byte server seed, and returns only its SHA-256 commitment inside the prepared ceremony response. No card ID, orientation, or assignment exists yet. A normalized same-question check can instead return the retained reading during the configured cooldown.
7. The browser creates a Web Crypto nonce before shuffling and XOR-mixes another independent 32-byte contribution for each intentional stir. After shuffle/cut completion or skip, the tarot domain derives independent HMAC-SHA-256 permutation and orientation streams from the server seed, final client nonce, and immutable session/version coordinates, performs unbiased Fisher–Yates, rotates by the selected cut, and assigns cards to the previously snapshotted positions. The domain signature accepts no profile, question, classifier, meaning, payment, or AI input.
8. The complete draw, reading session, and durable interpretation job are committed atomically before dealing. The reading separately references its immutable profile snapshot. `question-trait-lens-v2` sends only relevant plain-language traits and preserved tensions when `personalized_tarot` is selected; `pure_tarot` sends no profile lens. Raw birth facts and calculation payloads stay out.
9. Schema-validated `reading-result-v3` output stores a direct answer, overall pattern, exact card/position/orientation evidence, relationship notes, coherent synthesis, agency, reflection, uncertainty, and a separately labeled personalization audit record. In personalized mode, eligible lens statements shape the actual concise consultation prose rather than appearing as a standalone explainer. Trajectory, alternate path, and timing are nullable and validated against the snapshotted spread capabilities. Persisted v1/v2 results normalize at the repository boundary. Unsafe or failed live output falls back deterministically; retries and valid clarifying follow-ups reuse the same draw.

Step 8 uses a durable, idempotent job (migration `0007_interpretation_jobs`, extended by `0025_committed_draw_lifecycle`): finalization enqueues the job in the same transaction as the locked draw, then makes one best-effort inline attempt. An interrupted or transiently failed attempt remains claimable; a Netlify-scheduled function drains it within about a minute, and the client polls rather than assuming its first fetch is current. Prepared ceremonies do not enqueue work. See [Deployment](DEPLOYMENT.md) and [Known gaps](KNOWN-GAPS.md) for worker authorization and remaining manual-review gates.

The provider transport defaults to direct server-to-server Groq. A custom HTTPS `/v1` origin is accepted only as an explicitly approved, exact-host-pinned, Cloudflare Access-protected narrow gateway with a distinct application bearer; direct-provider and gateway credentials are mutually exclusive. The app rejects loopback/IP/custom-path origins and incomplete Access configuration before sending a request. `infra/cali-tokenpak` supplies a default-off segmented blueprint: named Tunnel → prompt/schema gateway → isolated TokenPak → fixed Groq-key-injecting egress broker, plus a separate fixed Access-JWKS relay. It publishes no ports and gives TokenPak no host/repository/private-data mounts. Host egress enforcement and the adversarial pilot remain external gates defined in [AI gateway and tunnel security](AI-GATEWAY-SECURITY.md) and [the Cali pilot runbook](CALI-TOKENPAK-PILOT.md). TokenPak remains a proxy to Groq, not the inference model, and is never the tunnel origin.

Report Checkout is a separate stateful path. Before redirecting, the server stores the pending order with a context-bound encrypted, name-stripped copy of only the derived profile data required by the report. Stripe receives the opaque order ID, not that source. A verified paid event atomically marks the order paid, grants its single entitlement, creates one pending report, moves the encrypted source into one `report_jobs` row, and clears the order copy. The webhook acknowledges without generating prose. The same scheduled drain claims report jobs with leases and capped backoff; successful generation writes all structured sections and clears the temporary source, while terminal failure remains user-retryable. Purchased reports have a standalone authenticated history and an authenticated, tagged PDF generated from the same presentation model as the web view. Profile deletion nulls commerce snapshot pointers but leaves paid reconciliation and generated report content intact; account deletion still cascades the subject's rows.

Support and operations use a separate server-only authorization boundary. `SUPPORT_USER_IDS` may inspect aggregate queue health, closed product-event counts, effective configuration, and exact opaque trace IDs; trace results contain only entity kind, status, and timestamp. `OPERATOR_USER_IDS` inherits that visibility and may rate-limitedly retry only retained failed jobs. Operators also manage an app-only runtime control plane: validated domain drafts require approval from a different operator before atomic publication, prior approved versions can be rolled back, deck/spread/product activation is audited, and emergency actions can only make AI, models, or payments more restrictive. The reviewed content release names deck, card set, meanings, spread catalog, and interpretation-rules versions explicitly.

Privacy-safe product measurement is first-party and app-only. A closed event/property schema rejects arbitrary strings and content; database constraints enforce the same vocabulary, and idempotency identifiers are stored only as SHA-256 digests. The scheduled durable-job trigger receives aggregate auth/profile/AI/payment/latency/volume counters and queue age/depth, evaluates fixed alert classes, and may send a content-free JSON alert to one configured HTTPS receiver. Provider-native billing, uptime, and database alerts remain deployment gates.

The profile engine never calls consumer chart websites. Geographic planetary angularity will reuse the approved Western ephemeris and normalized UTC/coordinate context. Nine Star Ki is calculated locally from an explicit versioned civil-date and Lo Shu convention; no third-party guide, calculator, prose, or artwork is ingested. Paid-report synthesis consumes only persisted versioned component output and original StarGuidance editorial rules.

## Immersive reading presentation

The shared shell uses one semantic token system, restrained CSS-only atmospheric layers, readable focus treatments, and route-specific composition rather than a generic dashboard frame. Onboarding presents all four birth details in one centered form: birth name/date are visibly required, while birthplace/time have independent “I don't know” controls. It exposes no calculation-system or capability taxonomy. Reading selection begins with the reflective need and then recommends a configurable spread; all six spreads remain directly selectable.

The ritual route keeps one `MysticSanctuaryScene` mounted across question/spread confirmation, focus, shuffle, optional cut, finalization, deal, reveal, interpretation, retry, and follow-up. CSS-only mist, light, particles, and phase-responsive color surround responsive AVIF/WebP art. Ambient setup uses the original sanctuary, while card, reading, and next-action stages use a dedicated clear starry-night desktop/portrait composition with a dark central field. `TarotSpreadStage` and `PhysicalTarotCard` render dealt cards with a true front/back transform, a card-specific v3 SVG face, and orientation-appropriate baseline themes. Exactly 78 lightweight anonymous backs move through six planar streams, but none is a full card component and none contains identity or assignment state; the real deck exists only inside the finalization boundary. Swipe/tap/keyboard stirs update the pending nonce, while an immediate finish retains its initial secure value. Procedural Web Audio cues are short, optional, and generated only after user interaction; no tracking or remote audio asset is involved. Authenticated reading audio is a separate default-off boundary: a configured Fish Audio adapter is never invoked by shuffle, reveal, interpretation generation, page load, or preference changes.

The gather phase advances to a real optional-cut decision. Selecting a cut rotates the finalized permutation by that exact offset; declining records offset zero. Finalization then persists every assignment before dealing. Exact revealed-card indexes are persisted monotonically on authenticated readings; browser session storage is a fallback, while the guest receipt guarantees exact-draw recovery. Every remaining face-down position is a keyboard/touch/click control, so reveal order is the reader's choice; Reveal All is explicit. This changes presentation order only. A reveal shows only that card's name, orientation, position, and concise baseline; identifying attributes and whole-reading prose remain absent for unrevealed cards. Interruption returns to the same draw, while an expired TTL enters the explicit recovery state. Motion and sound choices persist in account settings with local/OS fallback; skip animation follows the same entropy and result rules.

`OracleTranscript` receives nothing until every card is revealed and `fullSpreadReady` has been reached. At that boundary the physical spread remains visible above a smaller centered reading window. That window renders exactly one concise passage at a time: the direct answer, each evidence-backed card/position interpretation, the combined cross-card thread, supported outlook, agency, and final reflection/uncertainty. Pure Tarot has no profile input. Personalized Tarot silently carries eligible profile observations through the consultation prose while retaining a labeled audit record in the collapsed evidence details. During opted-in full-reading narration, Fish word timings progressively reveal the current passage, advance the window section by section, and add a restrained aura to the card positions referenced by the active passage. Network-stream completion does not expose follow-up UI: the reader must explicitly finish the final passage. The spread and transcript then unmount and the closing threshold appears before the reader may choose a same-draw clarification or seal the reading.

When the server confirms a complete Fish Audio configuration, signed-in readers may opt into an `Audio reading` preference. That preference only reveals a play control. A play action posts the reading target and phase sequence—not prose—to the authenticated route; the server re-loads the owned persisted result, verifies the reveal gate, selects that exact schema-validated passage, and streams only its heading and text through Fish Audio's timestamped speech endpoint. The browser assembles one passage at a time, keeps only numeric word timing metadata beside the audio, and requests the next passage only when continuous playback reaches the previous passage's end. Each completed section is written to a bounded origin-scoped Cache Storage namespace (at most 64 sections and 64 MiB, with a 12 MiB per-section limit); later page loads replay that entry without calling Fish until browser eviction, explicit corrupt-section retry, or site-data clearing. Page-lifetime object URLs remain separate from this persistent cache. Stopping playback prevents future sections from being requested. The guest and synthetic-preview lanes remain outside this network-voice boundary.

Completed history entries open `/reading/[id]`, a pre-revealed result scene that does not replay shuffle, cut, or reveal. The history surface renders a visual timeline using version-appropriate thumbnails from each locked draw, retains the same spread-aware transcript, exposes the configured remaining follow-ups only after the reader explicitly finishes reviewing the interpretation, and submits private feedback through a separate authenticated resource.

`PersistedResultStreamAdapter` converts only a validated, persisted `readingResultSchema` object into the passages actually supported by that spread. The authenticated Next.js route refuses to emit those passages until persisted reveal progress covers every locked position, then streams NDJSON through `ReadableStream` with `no-store` and buffering disabled. It never receives or emits the private question. A transport failure preserves already rendered chunks; retry reads the same persisted result and draw.

The noindex `/visual-preview` route uses synthetic, non-personal fixtures for deploy-preview screenshots. A Netlify context-specific environment flag enables it for deploy previews; the flag defaults off and public production returns 404.

## Package ownership

- `contracts`: boundary schemas and shared trait ontology.
- `database`: 33-table relational model, migration metadata, RLS policy SQL, durable queues, runtime configuration, first-party operational signals, and encryption primitives.
- `tarot-domain`: selection, reversal, locking, and follow-up lineage invariants.
- `tarot-content`: original content, attribution, versions, six selectable spreads, spatial layout metadata, deterministic one-/three-card context templates, and retired definitions used only to resolve historical locked draws.
- `reading-machine`: valid ritual transitions, failure, expiry, and high-stakes states.
- `ai`: safety rules, reading-lens selection, provider interface, validation, and fallback.
- `design-system`: reusable accessible UI primitives.
- `config`: feature/environment parsing.

## Runtime adapters

The selector has no default. `supabase` activates hosted Auth and Postgres repositories; `local` activates the in-process test adapter only after a second explicit allow flag and only in development/test. Deploy previews select `supabase`, so missing credentials produce a closed authentication/persistence boundary instead of silently creating volatile sessions.

The repository contract exposes users, settings, versioned consent, profiles, snapshots, components, traits, sessions, draws, outputs, configurable follow-ups, history, experience/outcome feedback, reports, atomic report fulfillment, orders, entitlements, webhook events, runtime configuration, privacy-safe product events, audit, export, and deletion. Supabase requests use a pooled server-only SQL connection inside a transaction that assumes the non-login `starguidance_app` database role and sets the verified Auth subject. Follow-up count-and-insert is serialized by locking the owned reading row, so concurrent requests cannot exceed the published limit. Supabase reads the published runtime policy and intersects it with seeded deck/spread/product `active` flags, so a database kill switch can only remove capability. The browser's `authenticated` role has no private-table privileges. Cross-user queue claims have explicit connection-role policies; user retries remain subject-bound. Service operations are constructed separately and are limited to explicit webhook/operator boundaries and Auth identity deletion. Profile-report purchase and webhook entry points also retain the default-off server environment gate; browser state never grants authorization.

Profile updates append a snapshot and change only the active pointer. Reading rows retain their original snapshot foreign key. Draw finalization commits the session, full draw, and interpretation job atomically before any provider runs; retry appends output without writing the draw.
